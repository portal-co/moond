PSEUDOCODE BODY WRITING GUIDE

Purpose
- This guide is intended to be fed to a future Copilot/Copilot-like agent to write the bodies of the C-like pseudocode files under ref/block2/pseudocode/ (and subsequently ref/block1/pseudocode/). It collects the repo conventions, authoritative references, common micro-op patterns, helper names, TODO handling, and commit/operational rules.

- Machine instruction reference: ref/moon/agcis_2_machine_instructions.pdf (AGCIS Issue 2) — useful pages: 15–36 (TC/STD2/XCH/NDX/AD/SU), 46–60 (MP), 61–80 (DV), 86–102 (misc: PINC/MINC, SHINC/SHANC, RPT, GO/TCSA/OINC/LINC).

General style & requirements (apply to every pseudocode body)
- Language: C-like pseudocode using familiar primitive types. Use uint16_t/int16_t for 16-bit words. Where 15-bit fields matter, indicate (u)int15_t in prose and comments. Use 0o prefix for octal (e.g., 0o20).
- Header: include "Generated by AI - C-like pseudocode", source file, references (AGCIS pages), and timestamp.
- Function signature: use descriptive names matching instruction mnemonics, e.g. void AD_K(address_t K) { ... }.
- Structure: follow this canonical layout inside each function:
  1) STMIC/Memory inquiry (only if instruction reads memory K): word_t k = MEM.read(K); test_parity(k);
  2) Load CP registers needed: word_t a = A; word_t b = B; word_t lp = LP; // etc.
  3) Core operation: implement the arithmetic/logic/branch/shift; prefer use of provided helper routines (see helpers list).
  4) Overflow/edge handling: check add_with_flags results and schedule OVCTR updates (signal_OVCTR_increment(), signal_OVCTR_decrement()) rather than directly modifying OVCTR unless the instruction is PINC/MINC.
  5) Write-back: MEM.write(K, value) using set_parity_field before write if storing to memory.
  6) Finalize: schedule STD2 or equivalent via SQG.execute_STD2(); or set Z/Q explicitly if instruction semantics require.
- Subinstructions: for multi-part instructions (e.g., MP0..MP3, DV0/DV1), annotate the subinstruction sequence with inline comments and where helpful inline small helper bodies with a short "Inline notes" block explaining why it was inlined (per parity rules for Block-2).
- Inlining rule: Block-2 prefers small inlined helper bodies when they relate to timing/subinstruction fusion; add an "Inline notes" comment above the inlinee pointing to the canonical helper in ref/Instruction.md or ref/STD2.md.

Standard helper primitives (use these names verbatim)
- word_t MEM.read(address_t addr)
- void MEM.write(address_t addr, word_t value) // sets parity bit via set_parity_field(value)
- void test_parity(word_t w)
- sum_t add_with_flags(word_t x, word_t y) // returns {value, overflow, underflow}
- product_t signed_multiply_14x14(word_t a, word_t b) // returns high/low parts
- division_result_t agc_divide_approach3(word_t dividend, word_t divisor) // AGC approach 3 for dividing
- word_t extract_high(product_t p), extract_low(product_t p)
- void SQG.execute_STD2(void) // schedule STD2 sequencing
- void schedule_PINC(void), schedule_MINC(void) // route to Counter Priority Control
- void signal_OVCTR_increment(void), signal_OVCTR_decrement(void)
- bit_t test_bit(word_t w, int pos), word_t set_parity_field(word_t w)
- void inhibit_interrupts(void), void signal_UPRUPT(void)

Instruction pattern notes (examples)
- AD K (Add Data from K): use add_with_flags(a, k), A = result.value; if overflow -> schedule_PINC or signal_OVCTR_increment(); call SQG.execute_STD2(); restore K if in restorable range per AGCIS.
- XCH K (Exchange A with K): e = MEM.read(K); test_parity(e); temp = A; A = e; MEM.write(K, temp) but apply AGCIS bit movement rules (bit16/bit15 transfers) when writing; comment the rules with a reference to AGCIS Issue 2 pages on XCH.
- MP K (Multiply): clear OV bit in A, call signed_multiply_14x14, store high in A and low in LP; annotate the MP subinstruction sequence and MPCTR behavior; in Block-2 inline small multiply steps if needed for timing.
- DV K (Divide): use agc_divide_approach3 to produce quotient and remainder; put quotient in A and remainder (complemented absolute) in Q per AGCIS; handle special cases (|a| == |k| etc.) as documented and mark ambiguous cases TODO:VERIFY if not clearly covered by AGCIS pages.
- NDX K / EXTEND: compute B = z + K, handle possible order-code overflow becoming an Extra Code (document bit-level ordercode behavior), and annotate STD2 sequencing.

Register & bit movement rules
- Follow AGCIS Issue 3 guidance: when transferring between G and flip-flop registers, bit16/bit15 movement rules apply (bit16 moves into 15 when moving into some registers, parity bits only go to P position 0, etc.). Cite ref/moon/agcis_3_central_processor.pdf pages 3–11 in comments near code that performs register transfers.
- Canonical types: document and use (u)int15_t when extracting 15-bit fields; use sign_extend15 helper where required (documented in ref/cpu/registers.md).

Edge cases and TODO tagging
- Always mark ambiguous or training-derived results as TODO:VERIFY with a one-line rationale (e.g., "TODO:VERIFY — inferred from OCR on AGCIS page X or from training model; no explicit PDF citation found"). Keep these entries concise and searchable.
- If a behavior is unknown (e.g., hardware race or missing memo), mark the result as UNKNOWN and add a short note which sources were checked.
- Add any new authoritative citations to the instruction file (PDF path + page numbers) when resolving TODOs.

Commit and workflow rules (for the Copilot agent)
- Commit messages for automated/AI edits MUST start with "[AI]" followed by a concise description and an ISO timestamp (e.g., "[AI] Expand AD_K pseudocode — 2025-12-07T09:00:00Z").
- Do not modify git config (author/committer). Use git mv for any file moves so Git history is preserved.
- Keep ref/TEMP_INSTR_CHANGES.md entries until a human reviewer removes them; do not delete pending entries automatically.

Review checklist (what a human reviewer will check)
1) Does the function header include source and AGCIS page citations where assertions are made?
2) Are helper functions used consistently and named per the guide? If inlined for Block-2, is an "Inline notes" block present explaining why?
3) Are all occurrences of ambiguous or hardware-dependent behavior marked TODO:VERIFY with rationale?
4) Are parity and bit-movement rules documented in comments near relevant code lines with citations to AGCIS Issue 3?
5) Is the commit message formatted per the rule and did the agent avoid changing pending list entries?

Example (AD K minimal body)
void AD_K(address_t K) {
    word_t a = A;
    word_t k = MEM.read(K); test_parity(k); // AGCIS Issue 2 p. 33
    sum_t r = add_with_flags(a, k);
    A = r.value;
    if (r.overflow) signal_OVCTR_increment();
    else if (r.underflow) signal_OVCTR_decrement();
    // restore K semantics per AGCIS when applicable
    SQG.execute_STD2();
}
